# 数据内容开发合同

本合同规定 `data/` 是游戏静态内容与可调规则的唯一来源。JSON 不能只是给 Python 常量
补名字、做清单或保存发布备注；运行时行为必须实际读取对应配置。代码保留通用算法、状态机、
权限、事务和持久化，不再重复定义某一境界、道途、物品、任务或奖励的具体参数。文档方案版本
不进入游戏运行配置、数据库快照或 Python 常量。

## 1. 数据与代码边界

| 内容 | 权威来源 | 示例 |
|:--|:--|:--|
| 内容及展示 | `data/` | 名称、`desc`、品质、技能效果、材料、装备、任务文本 |
| 可调整的玩法规则 | `data/` | 境界/道途适用范围、成本、数量、权重、冷却、奖励池、前置条件 |
| 通用执行过程 | Python | 权重抽取算法、战斗结算、悬赏状态机、资源事务、幂等与权限检查 |
| 角色正在发生的状态 | 数据库 | 接取的任务、玩家进度、冻结快照、随机结果、资产流水 |

如果改一个境界、道途或物品的成本、效果、候选范围和奖励仍需改 Python 分支/字典，说明
配置合同尚未闭合。不得以“规则代码”名义把内容表、境界名单、道途名单、奖励清单或数值
重新硬编码。通用公式可以留在代码中，但公式参数必须从配置读取。

## 2. JSON 记录合同

文件由 `data/内容清单.json` 注册，领域记录由 `ContentBundle` 按 `(kind, key)` 索引。
文件拆分服务于领域归属；代码按稳定键与字段读取，不按数组顺序或文件名推断业务含义。

可面向玩家展示的记录使用统一字段：

```json
{
  "key": "bounty.foundation.body.training",
  "name": "筑基试炼",
  "desc": "击败训练傀儡，磨炼近身攻势。",
  "status": "active",
  "quality": "rare"
}
```

- `key` 是稳定、全局唯一的 ASCII 键；跨记录引用使用带类型的字段，如 `item_key`、`reward_pool_key`。
- `name` 是显示名称；`desc` 是介绍。新记录不得只加 `name` 而缺少 `desc`。
- 品质统一为 `common`、`uncommon`、`rare`、`heaven`、`mythic`；品质本身不能替代准入条件。
- `status` 表示内容是否可被对应流程采用，不代表该玩法已经拥有玩家入口；入口开放仍由
  [当前开发状态](current-status.md)裁决。
- 内容 JSON 不添加 `generated_at`、`schema_version`、`content_version`、`rule_version`
  等无业务用途的时间或版本字段。不要为“兼容旧格式”保留旧字段、旧别名或 Python 回退表；
  尚未正式发布，合同变化时统一改数据和消费代码。
- 配置错误必须在内容包加载/校验时明确失败并指出文件、记录键和字段；不得静默跳过坏行、
  用默认数值继续运行，或吞掉引用缺失。
- JSON 对象重复字段、清单重复注册文件、重复 `(kind, key)`、缺少必需字段或字段类型错误，
  都是配置错误。只有清单文件确实不存在时 `load_optional` 才能返回 `None`；清单存在但内容损坏必须失败。

## 2.1 加载缓存和基础设施边界

跨领域只读 JSON 缓存由 `xiuxian/utils/json_cache.py` 提供：调用者拿到独立副本，避免修改缓存对象；
文件变更后下一次读取必须重新解析。缓存不能掩盖 JSON 错误，也不能把坏文件降级为空列表或内置默认值。

`xiuxian/utils/database.py` 只统一连接初始化参数。`xiuxian/persistence/` 管理 schema、事务、迁移和
通用存储协议；领域 repository 负责本领域查询与写入。玩法数值解析不能放进 `utils`，避免通用层
变成另一份规则字典。

项目尚未正式发布，数据库 schema 和测试夹具允许直接重构，不保留旧格式兼容分支。测试数据库应放在
临时目录或明确指定的测试路径。清理开发数据库前先确认目标并备份；运行时、测试和安装脚本不得
自动删除用户持久化目录中的数据库。

## 3. 可变因素和内容矩阵

需要因境界、道途、职业、地点、阵营、队伍规模或活动轮次而变化的内容，应将这些因素作为
配置维度，不在代码里写 `if realm == ...` 的内容映射。配置可以为多个维度提供候选项和权重，
由同一个运行时选择器完成过滤与抽取。

例如悬赏定义至少分成“任务候选”和“奖励池”：

```json
{
  "key": "bounty.foundation.body.training",
  "name": "筑基体修试炼",
  "desc": "在演武场击败训练傀儡。",
  "status": "active",
  "realm_keys": ["foundation"],
  "path_keys": ["body"],
  "weight": 100,
  "objective": {
    "type": "battle_wins",
    "target_key": "enemy.training_dummy",
    "amount": 2
  },
  "reward_pool_key": "reward_pool.bounty.foundation.body"
}
```

`reward_pool_key` 指向 `data/奖励/奖励.json` 中独立的加权奖池。不同境界和道途可以引用
不同任务池，也可以共享任务但引用不同奖励池；增加新境界或道途应只需添加配置记录和对应
测试，不应新增 Python 分支。

加权奖池使用 `pool_type=weighted`、正整数 `weight` 和非空 `rewards` 映射。奖励键只能是
当前内容包中的物品、灵石、角色资源或阵营声望；物品引用必须闭合，数量必须为正整数。
需要多次独立抽取的内容可以把联合结果展开为笛卡尔积，并将各次权重相乘，保证改为内容池
后不改变原有联合分布；零数量产出不写入结果映射。
奖池可用 `item_weight_bonus: true` 声明福缘提高含物品结果的权重；字段必须为布尔值，未声明
时不应用此因子。权重因子不改变声望、资源或明确无收获结果的基础权重。

## 4. 随机、快照和幂等

随机流程固定为：

1. 从玩家/队伍当前快照读取境界、道途、职业、地点、阵营及当前轮次等适用因子。
2. 用配置过滤不满足前置的候选项；无候选项时返回显式的“无可用内容”，不悄悄改用默认任务。
3. 依据配置权重、配额和服务端随机种子选择任务，再从其奖励池抽取奖励。
4. 在创建 offer 的同一事务冻结候选来源、任务键、目标、奖励池键、实际奖励、输入快照和随机证据。
5. 完成和领取只读取冻结快照；相同 `operation_id` 回放原结果，不同输入冲突，不得重新抽取。

悬赏榜预览可以展示候选范围/奖励范围，但只读查询不得创建 offer 或消耗配额。任务被接取后，
榜单、数据热更、重启和跨适配器切换都不能改变该 offer 的目标或奖励。

固定任务以 `data/任务/任务.json` 的触发定义为准。`claim_group=guidance` 的任务必须声明允许的
来源 `operations` 和结果字段 `result`；结果对象逐字段匹配服务端 operation 账本中的结算结果，
`one_of` 只表示该字段的有限允许值。触发证据始终限定当前角色，客户端不能提交来源编号或进度。
任务领取与奖励发放、`quest_events`、`quest_progress` 和领取 operation 在同一事务提交；重放读取
原奖励/来源快照，不重新解析现行奖励内容。

## 5. 数据驱动完成门槛

一个数据域只有同时满足下列条件才可标为已完成：

1. JSON 含完整业务字段，且是运行时唯一来源；代码中没有重复的内容表或默认值。
2. 内容加载校验稳定键唯一、字段类型正确、品质覆盖、所有引用闭合、前置表达式受支持。
3. 实际消费路径读取并执行 JSON 中的参数；单测通过修改临时配置证明行为会随配置变化。
4. 随机内容覆盖权重边界、无候选、种子回放、offer 冻结、重复 operation 和奖励原子性。
5. 展示文本从 `name`/`desc`/物品注册表取值，不再维护另一份标签映射。

只把配置登记进 manifest、增加盘点表或往记录里塞 `desc`，不代表玩法已数据驱动。

## 6. 当前差距和迁移优先级

| 内容域 | 当前实际消费 | 尚未闭合 |
|:--|:--|:--|
| 境界 | `progression/rules.py` 从境界记录读取层数和阈值 | 其他晋层参数仍待配置化；新增境界时不应维护第二份 Python 境界名单 |
| 物品 | 可用物品和部分装备名称从内容包加载 | 物品效果、标签和消费行为仍有专用 Python 定义/白名单分支 |

| 常驻经营公共项目 | `data/生活/生活.json` 的 `public_project` 记录提供项目需求、贡献资源、效果、奖励、权限和服务来源；运行时由 `public_project_definitions()` 校验并消费 | 其他生活域仍需按垂直切片迁移，不能在规则模块新增项目数值表 |
| 虚空塔高层 | `data/特殊/虚空塔.json` 的 `void_spire` 记录提供楼层段、准入、体力、周限、敌人范围、首领、奖励、故事和称号稳定键；敌人和图鉴分别引用 `data/战斗/虚空塔.json`、`data/图鉴/虚空塔.json` | 新路线必须补齐段记录和引用校验，不能只修改楼层常量 |
| 任务/事件/配方 | 四项引路任务由 `claim_group=guidance`、服务端 operation 结果条件和奖励引用驱动；寻仙、入道、近郊采集和成功生产结算均可作为本人证据，奖励与任务进度同事务提交。魔界入侵、妖界贸易和界隙裂痕从事件记录解析轮次、目标、来源贡献及个人门槛，并在新轮次创建时冻结配置和奖励；贸易键、队伍类型、物品及声望资源引用均校验，来源和领奖使用共享资产/数值事务 | 其他任务/事件/配方仍需按独立切片迁移；来源必须来自本人已结算的服务端记录 |

推荐顺序：统一内容校验和读取 API；技能/体质增长参数；扩充悬赏境界/道途任务矩阵与奖励池；探索/战斗
及任务事件奖励；再逐个迁移生产、生活、社交等配置。每完成一个域，更新本表和
[当前开发状态](current-status.md)，不把尚未接通的内容写成已完成。

技能成长记录只保存稳定技能键、各技能上限、等级成本和受成长影响的效果字段；展示名、介绍、道途与
基础效果从技能记录读取。成本以资源稳定键引用资源内容，资源名称和存储列归资源记录。效果增量按配置
指定字段通用应用，不可假设所有技能都增长 `effect.value`。数据库只保存角色已参悟的技能键、等级和
结算快照，不重复保存静态道途或等级上限。
