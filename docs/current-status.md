# 当前开发状态

本文只回答一个问题：**当前分支哪些能力已经可以运行，哪些仍然只是规则或内容合同**。
它不是玩法规则的第二份定义；规则、数值、稳定键和完整路线仍以[完整内容开发总表](content-development.md)
及各域的 `model.md`、`workflow.md`、`use-cases.md` 为准。

## 1. 状态定义

| 状态 | 含义 | 是否允许新增运行时入口 |
|:--|:--|:--:|
| `open` | 已有 application 用例、持久化、幂等和适配器测试，可供玩家使用 | 是 |
| `partial` | 已有局部运行时状态机，但上游任务、资产来源或最终结算尚未对玩家开放 | 否，不能把夹具前置当作玩家入口 |
| `contract` | 已有完整规则、稳定键和测试夹具，但尚未接入运行时 | 否 |
| `locked` | 已登记内容或接口，前置条件尚未满足，统一返回内容未开放 | 否 |
| `planned` | 已列入开发路线，尚未完成规则闭合 | 否 |

`content-v0.1` 至 `content-v0.6` 是发布快照，不代表当前状态，也不代表代码开发顺序。
快照中的 `open` 只表示该版本发布时计划开放；本文件中的 `open` 才表示当前代码已经接入。

## 3. 当前未开放或端到端不完整

以下内容可以在文档中有完整设计，但当前不能创建可运行会话，或尚不能由玩家端完成完整流程：

| 范围 | 当前状态 | 开放前置 |
|:--|:--|:--|
| 自动回合战斗 | `contract`/`locked` | 角色、属性、装备、技能、队伍、事务和回放门槛全部通过；当前仅开放终局战前置预览，队伍只开放状态机 |
| 单人/多人 PVE | `contract`/`locked` | 战斗运行时后置；只能使用规则、接口和测试夹具 |
| 1v1/多方 PvP | `contract`/`locked` | 服务端自动选行动，客户端不得提交攻击、技能、目标或结果 |
| 秘境、遗府、试炼塔、竞技场、派遣、完整图鉴剧情 | `locked` | 依赖战斗或未完成的特色玩法切片 |
| 灵兽与灵骑 | `locked` | 实体成长、装备、休养和 BattleSnapshot 规则完成后再接入 |
| 多人队伍/匹配、宗门扩展和完整世界事件 | `planned` | 社交/经济/活动域的状态机、锁定和恢复演练完成；宗门基础成员闭环、师徒关系、双人队伍状态机、固定摆摊、生产委托、灵泉事件、城镇委托、基础服务订单、短途运输与地方公共项目闭环已开放 |
| 高阶境界与终局 | `partial` | 合道/渡劫非战斗状态机、试炼顺序、资格预览和结局选择可运行；三界正式区域、任务生产者、终局配方、道源任务和最终战仍未开放，玩家无法端到端获得所有高阶资格 |

`quest.prepare_nascent_soul` 是上述任务中唯一已有玩家命令生产者（`准备元婴`）。其余三项
突破许可目前只由消费端校验；高阶测试会明确用 SQLite 夹具构造资格，以验证状态机而不是
声称这些任务已可由玩家完成。

终局来源数值还有一项待实现前统一的闭合校验：`extensions/content/content-v0.6.md` 规定三次
试炼与三项道源任务合计应提供 `ascension_merit=1,000`，而现有运行时试炼奖励和未实现任务
生产者尚未形成可验证的端到端总和。实现道源任务时必须先固定单一奖励表、同步
`foundation/progression/content-v0.6.md` 和公式测试，再开放最终战。

## 5. 开发顺序

开发按可独立验收的垂直切片推进，不按 `content-v0.1`、`content-v0.2` 逐个版本搬运：

1. 稳定当前已开放切片的迁移、回放、并发、资产锁和 QQ/OneBot 适配器契约。
2. 对照战斗域完成自动回合最小闭环：训练夹具、单人 PVE、可回放会话、失败恢复和奖励唯一性。
3. 以已完成的战斗会话为唯一证据，实现 `quest.soul_transformation` 与 `quest.break_void` 的任务生产者；随后接入对应突破，不写入测试式资格标记。
4. 实现 `quest.dao_union`、三项道源任务、终局配方和飞升凭证，先通过终局资源可达性公式测试。
5. 最后开放多人终局战、候选生成、赛季三榜和展示结局；再推进 PvP、跨服与完整三界区域。

每个新切片必须同时提交规则、application DTO、迁移、适配器、测试、观测字段、关闭新建
语义、历史会话处理和回滚步骤；只有满足[首版验收门槛](content-development.md#22-首版验收门槛)
才可把状态从 `contract`/`locked` 改为 `open`。

## 6. 文档维护规则

- 改玩法边界、境界或跨域依赖：先改 `content-development.md`。
- 改实体、状态机或用例契约：改对应域的 `model.md`、`workflow.md` 或 `use-cases.md`。
- 改当前实现状态：只改本文，并在对应域 README 保留链接，不复制整张状态表。
- 改历史发布参数：只改相应 `content-v*.md`，同时说明 `content_version` 和 `rule_version`。
- 代码、命令处理器和测试不得自行创建与文档冲突的第二套规则。
