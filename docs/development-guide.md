## 运行链路

适配器负责把平台输入归一化为命令上下文，并呈现 application 的结果；CLI、QQ、OneBot 与 Web 不重复实现领域规则。Application 组织用例和权限，领域服务/规则解释内容，repository 在持久化事务中执行状态变化。跨入口玩法必须调用同一 application 与 repository。

静态玩法数据由 `data/` JSON 提供，并通过清单、严格解析和 `ContentBundle` 取得。每项开放内容都需要真实的公开入口、可达来源和实际消费者；数据记录本身或 `status=open` 不代表玩家可执行。名称、文案、奖励和可调参数随记录读取，通用状态机、权限和事务留在代码中。

资产写入通过 Unit of Work 与领域 repository 完成。operation、账本、快照和奖励应按领域合同在同一事务内提交；失败回滚后，同一请求必须能按既有语义恢复或重试。数据库结构变化通过迁移保留已有角色数据，不以删库重建替代迁移。

## 变更流程

1. 从玩家入口沿 application、领域服务、repository 和持久化追踪当前行为，同时找到声明内容的生产者及其真实消费者。
2. 阅读受影响领域合同；数据变更同步验证稳定键、跨文件引用、公开来源、准入条件和结算用途。官方种子遵守[发布与种子迁移](release-distribution.md)，保留未知与自定义宿主数据。
3. 内容、规则与入口一起完成。需要异步、剧情或经济结果时，明确快照、失败、取消、过期、重启、重复请求和并发语义。
4. 按[测试与验收](testing.md)运行直接调用方和受影响边界的定向验证，并检查文档链接与差异格式。仅有内容记录、测试夹具或模拟平台结果时，不将其描述为公开能力或真实平台验收。
5. 更新长期有效的公开说明和对应领域合同；具体运行状态、外部平台证据和版本发布状态分别按其适用范围记录。

领域 README 是对应子系统的索引；`model.md`、`workflow.md`、`use-cases.md` 说明实体和行为；`content-v*.md` 是版本化内容快照，不应被用来覆盖当前实现或玩家能力说明。
