# 领域与数据模型

## 1. 设计目标

新项目从逻辑模型开始，不把参考项目的 SQLite 表名当作 API。物理数据库可以
变化，但以下业务事实必须稳定：谁在什么时间、以什么请求、消耗了什么、获得
了什么，以及失败时是否完全没有资产变化。

## 2. 核心实体

| 实体 | 说明 | 典型不变量 |
|:--|:--|:--|
| `Player` | 用户在游戏世界中的角色 | 一个身份在一个世界只有一个活动角色；删除/封禁有明确状态 |
| `Progression` | 等级、境界、修为、灵根、炼体和轮回 | 经验/境界不能倒退，除非是明确的重置或轮回用例 |
| `Wallet` | 灵石、积分、声望和其它可计量资源 | 余额不可凭空为负；每次变化有来源和流水 |
| `Inventory` / `ItemInstance` | 堆叠物品与唯一装备/宠物 | 数量、容量、绑定和唯一性在同一事务内检查 |
| `Ability` | 功法、神通、身法、瞳术、增益和称号 | 学习、装备、卸下和效果计算可追踪 |
| `Session` | 修炼、探索、战斗、炼丹、拍卖和组队会话 | 会话只能沿定义状态机前进；过期/取消是显式终态 |
| `SocialLink` | 宗门、师徒、道侣、队伍关系 | 双向关系有一方权威；邀请/同意/拒绝可重放 |
| `MarketOrder` | 鬼市、仙肆和拍卖订单 | 资金/物品锁定，成交、撤单、过期只能结算一次 |
| `EventRound` | 活动、Boss、世界事件、赛季和轮次 | 轮次标识参与资格；领奖和贡献按轮次隔离 |
| `Operation` | 所有命令/Web/任务请求的审计与幂等记录 | 相同 operation key 返回同一结果，不重复改变资产 |

## 3. 资产不变量

1. 灵石、修为、积分、物品、体力、宠物经验、装备和奖励包属于资产；任何
   资产写入必须在一个用例事务中完成。
2. 预检查失败（用户不存在、权限不足、冷却、容量不足、状态冲突、参数无效）
   不改变任何资产，也不产生“成功”流水。
3. 随机奖励必须保存随机池/规则版本和实际结果，不能只保存最终余额。
4. 跨玩家交易先锁定再结算；锁定超时由定时任务回收，回收也要幂等。
5. 业务时间统一由 `Clock` 端口提供，禁止在领域规则中直接读取系统时间。
6. 数值使用明确的整数/定点语义；禁止依赖 SQLite 的隐式类型转换比较高境界经验。

## 4. 事务与幂等

每个改变状态的请求包含 `operation_id`（来自客户端的幂等键或服务端生成的
稳定键），并记录：请求类型、操作者、目标角色、输入摘要、规则版本、开始/结束
时间、状态、结果摘要和错误类别。

推荐状态：`accepted`、`applied`、`rejected`、`failed`、`expired`。重试时先查
相同 operation；若输入摘要不同，拒绝为冲突而不是覆盖旧结果。

## 5. 随机与规则版本

- 随机源通过端口注入，测试可使用确定性实现。
- 影响经济的随机池、掉落表、礼包和突破概率必须有版本号。
- 结算保存输入快照，不能在用户重试时用当前配置重新计算旧战斗。
- 管理员调整规则需要记录生效时间、操作者和旧/新版本。

## 6. 持久化建议

首版可以继续使用本地 SQLite，但以逻辑仓储隔离数据库细节：

- `game`：角色、成长、资产、操作流水和社交关系。
- `world`：地图、活动轮次、Boss、秘境和副本会话。
- `market`：鬼市、仙肆、拍卖和锁定资产。
- `ops`：任务、消息索引、备份、审计和运行指标。

是否合并数据库由基准测试和迁移风险决定，不以兼容旧文件名为理由。跨库
操作优先设计补偿/状态机；若无法保证原子性，必须让用户看到处理中状态，
并由恢复任务完成或回滚。

## 7. 迁移原则

- 每个领域拥有单调递增的迁移版本，迁移可重复执行。
- 迁移先增加兼容结构，再回填和验证，最后才删除旧结构。
- 任何历史导入都要有 dry-run、计数校验、错误样本和可恢复备份。
- 用户可见的旧字段通过投影层读取，不把旧 schema 传播到领域对象。
- 迁移脚本不得依赖 QQ 在线或外部网络。
