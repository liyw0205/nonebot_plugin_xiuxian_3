# 核心玩法：活动与任务

## 1. 任务类型

- 新手任务：引导身份、寻仙问道、第一次修炼和第一次生产。
- 日常任务：提供稳定但有限的行动目标，必须包含修行/探索与常驻经营候选。
- 周常任务：鼓励探索、宗门和生产协作。
- 道途任务：展示六大道途的差异。
- 世界任务：三界、洞天福地和阵营事件。
- 委托任务：玩家发布和完成的目标。
- 剧情任务：改变地点、关系、阵营或终局状态。

## 2. 任务定义

任务定义包括：任务键、版本、前置条件、目标、计数方式、时间窗口、消耗、奖励、失败、取消、重复策略和可见范围。

任务进度不能仅依靠消息文本推断，必须由服务端事件或明确的应用用例推进。

## 3. 周期窗口

所有日/周/赛季活动使用业务时钟和时区配置。窗口键示例：`daily:2026-01-01`、`season:1`。领取记录绑定窗口键，跨窗口不能重复领取。

## 4. 世界事件

世界事件可以是：

- 灵脉争夺。
- 魔界入侵。
- 妖界贸易。
- 洞天开放。
- 宗门协作建设。
- 灾害、遗迹或天象。

事件包含轮次、阶段、参与条件、贡献、个人奖励、阵营奖励、失败后果和结算时间。

## 5. 排行

排行按轮次保存快照，分别支持境界、战斗、生产、探索、宗门和事件贡献。排行奖励必须按快照发放，不随实时属性变化。

## 6. 活动商店

活动商店的兑换资格、次数、价格和库存绑定活动版本。活动结束后：

- 未领取奖励进入可追踪的待领取状态。
- 兑换次数停止增加。
- 未使用积分按活动规则处理。
- 不能通过修改客户端时间重新打开活动。

## 7. 赛季

赛季用于测试高阶内容、排行榜和世界变化。赛季结束时保存角色快照、奖励、称号和历史；赛季重置不应删除永久资产，除非文档明确说明。

## 8. 失败和重试

活动任务失败、超时、网络中断和重复点击都必须可重试或返回原结果。奖励领取和排行发放使用独立 operation。

## 9. 首版范围

首版实现新手任务、含居所/灵田/城镇委托/运输候选的日常目标、一次世界事件、基础贡献和活动奖励。赛季、复杂战令、多人首领和活动商店后置；每日奖励不直接作为无限修为来源。

## 10. 实现合同

### 10.1 任务和轮次字段

`TaskDefinition` 保存任务键、版本、类型、前置条件、目标表达、计数事件、时间窗口、奖励键、失败规则和可见范围。

`PlayerTask` 保存玩家、任务键/版本、窗口键、进度 JSON、状态、领取状态、开始/结束时间和 operation ID。

`EventRound` 保存事件键、轮次 ID、开始/结束时间、阶段、参与条件、贡献规则、奖励池、结算状态和规则版本。

### 10.2 任务推进

任务只能由白名单领域事件或明确用例推进，例如 `player_created`、`cultivation_settled`、`item_produced`、`battle_won`、`location_discovered`。

推进流程：读取任务版本 -> 验证事件主体 -> 计算增量 -> 写进度 -> 检查完成 -> 创建待领取奖励。事件重复消费必须由事件 ID 去重。

错误码：`TASK_NOT_FOUND`、`TASK_NOT_ACTIVE`、`TASK_PREREQUISITE_MISSING`、`TASK_WINDOW_CLOSED`、`TASK_ALREADY_CLAIMED`、`EVENT_DUPLICATE`。

### 10.3 世界事件状态机

```text
scheduled -> open -> running -> settlement -> settled
scheduled -> cancelled
open/running -> failed
```

阶段变化由任务或管理员 operation 驱动，不能通过客户端时间触发。贡献记录保存参与者、事件阶段、贡献来源和规则版本。

### 10.4 奖励领取

奖励先进入 `pending_claim`。`claim_event_reward` 验证轮次、资格、领取次数和奖励定义，然后调用统一奖励服务写入物品/灵石/修为/声望。

排行奖励使用冻结快照，快照生成后玩家属性变化不改变名次。未领取奖励在活动关闭后进入明确的邮箱、待领取或过期状态。

### 10.5 周期键

业务时钟生成 `daily:<date>`、`weekly:<year-week>`、`season:<id>` 等窗口键。窗口键写入玩家任务和领取记录，不能依赖客户端传入日期。

### 10.6 验收样例

1. 同一领域事件重复投递只增加一次任务进度。
2. 活动关闭后不能创建新进度，但允许按规则领取已完成奖励。
3. 奖励领取重试不重复生成资产。
4. 管理员提前结束事件会记录原因并执行明确结算策略。
5. 不同时区配置下，同一玩家的日常窗口边界由服务端 `Clock` 决定。
