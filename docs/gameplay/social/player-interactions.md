# 玩家互动开发说明

本文记录玩家直接互动的运行时现状、首期边界和验收约定；实际开放状态以[当前开发状态](../../current-status.md)和运行时入口为准。

## 现状与术语

| 玩法 | 当前状态 | 边界 |
|:--|:--|:--|
| `arena.spar` | 已开放 | 挑战公开发布的异步防守快照，计竞技场积分；不是对指定玩家发起的一对一邀请 |
| `arena.practice` | 已开放 | 快照持有人授权指定身份后进行不计分练习；仍使用竞技场快照，不建立玩家关系 |
| 玩家直接切磋 | 已开放 | 由玩家指定另一名玩家，立即观战一场中性斗法；不建对局、不计积分、不发奖励、不损资产 |
| 师徒 | 基础闭环已开放 | 支持邀请、接受/拒绝、过期和毕业；不要另建一套师徒关系 |
| 道侣 | 已开放 | 只记录双方同意的缘契生命周期，不共享修为、资产、任务或战斗加成 |

玩家直接切磋与竞技场不是同一模式。前者使用双方当下角色快照并即时演武；后者继续使用公开防守快照、竞技积分和现有反刷规则。切磋不复用 `arena.spar` 的计分或赛季投影。

## 直接切磋

### 首期流程

```text
输入目标 -> 读取双方快照 -> 服务端自动演武 -> 返回招式记录
```

命令：`切磋 <玩家>`。玩家参数使用道号；适配器只负责把事件归一化为 `CommandContext`，业务不区分 QQ、OneBot 或其他入口。

执行命令时校验双方角色状态，读取双方当下的属性、装备和技能快照。战斗复用自动回合规则，不接受客户端行动；环境固定为中性场景，回合上限从静态 JSON 读取。结果只随本次请求返回，不写入战斗会话、回放或图鉴。

切磋没有邀请、取消或等待过程，不设置押注、掠夺、装备耐久损耗、修为/资源奖励、竞技积分或胜负名望。观战不修改双方背包、钱包、修为、装备归属或关系状态。

### 持久化与失败边界

- 切磋不创建行动、资产锁、进行中状态或 operation 记录，可以和其他状态查询并存。
- 同一请求重复观战会按相同快照得到相同结果；不需要恢复任务，也没有可查询的切磋回放。
- 返回内容只展示双方道号、道途和必要招式信息，不展示平台 ID、背包或私密剧情数据。

## 道侣关系

### 首期流程

首期只实现关系生命周期，不把双修、共享修为、赠送资产或战斗加成混入关系创建：

```text
invited -> active -> dissolution_pending -> dissolved
    |         |              |
 rejected  dissolved      active (对方拒绝解除)
    |
 expired
```

命令：`邀请结为道侣 <道号>`、`接受道侣邀请 <关系号>`、`拒绝道侣邀请 <关系号>`、`道侣关系`、`申请解除道侣 <关系号>`、`确认解除道侣 <关系号>`、`拒绝解除道侣 <关系号>`。双方角色都必须明确同意；任何一方可提出解除，但只有另一方确认后关系才结束。解除请求过期或被拒绝时关系恢复为 `active`。管理裁决不纳入首期。

准入、邀请有效期、解除确认有效期、每人有效关系数、解除后的重结缘冷却等均从 `data/社交/玩家互动.json` 读取；当前内容要求双方元婴，解除后的同对冷却为三日。

关系状态只存在数据库，不在角色 JSON 中保存；邀请时将本次内容参数快照写入关系表。关系表保留双方角色 ID、状态转换时间、邀请/解除截止时间和对应 operation；唯一约束保证每人最多一段待确认/有效道侣关系。关系创建与解除不转移任何物品、货币、修为或装备。

只有新邀请读取当前开放的关系内容；邀请一经成立，接受/拒绝、查询和解除都使用邀请时冻结的准入、时限和同对冷却。接受时仍检查双方当前角色可用且境界达到冻结门槛，不能因新配置降低门槛而放宽旧邀请，也不能因提高门槛或关闭内容而阻断已有缘契。申请解除的截止时间与确认解除后的冷却均按同一份快照计算，拒绝或超时恢复关系时不替换规则。

历史 operation 在现行内容、期限和关系状态检查前回放；换输入会冲突，不会重复创建关系或解除。快照必须完整含九项邀请规则并严格校验，不接受缺字段、重复 JSON 键或隐式数值转换，不从现行配置补旧值。关系、成员占用和 operation 同事务写入，坏数据或写入故障整体拒绝，修复后原请求可重试。当前内容关闭仍拒绝新邀请，但不阻断已有关系的查询和履约。

### 后续玩法切片

- 共享日常/双人任务：单独定义任务目标、两人完成条件、每日额度、奖励归属和重复来源去重，再接入现有任务/事件结算。
- 双修：单独定义双方在线要求、地点、资源成本、冷却、增益上限和中断退款；不能默认直接共享修为，也不能绕过修炼准入。
- 关系展示：只展示双方同意公开的昵称和关系状态；解除后保留必要审计记录，不公开隐私历史。

这些后续切片不得用关系创建时的一次性奖励替代稳定玩法，也不得引入无法审计的双向资产变更。v0.3 的共享任务描述和 v0.6 的终局协作任务描述不是已实现功能；它们应在对应切片开发前重新核对奖励和规则。

## 师徒现状与扩展边界

现有师徒链已包含邀请、接受、拒绝、24 小时过期、毕业资格检查和一次性毕业奖励，并有 QQ 官方与 OneBot V11 命令链测试。当前师傅需达到筑基 L4 或更高境界；徒弟为凡人至聚气 L6；毕业要求徒弟已入道、达到聚气 L3，并完成一次生产或常驻经营服务。师傅最多收三名徒弟，毕业不直接发放修为或突破材料。

后续要补师徒功能时，应先补关系查询/本人关系列表和明确的解除规则，再考虑传承任务；继续复用 `mentor_relations` 与现有 `invite_mentor`、`accept_mentor`、`reject_mentor`、`graduate_apprentice` 用例。不得创建通用关系表来替换或重复实现已运行的师徒表，也不得让新的师徒任务重复结算毕业奖励。

## 配置、模块与测试约定

- 静态观战与道侣关系规则位于 `data/社交/玩家互动.json`；文件只配置场景、境界门槛和时限，不放玩家状态。
- 切磋规则属于战斗域；道侣状态机属于社交域。两者都通过 application 暴露适配器无关用例，只有改变角色关系的操作才进入 repository 事务与 operation ledger。
- QQ 官方和 OneBot V11 只需验证事件归一化后调用同一命令路径，不在业务层复制平台分支。
- 切磋测试覆盖自我切磋、未知玩家、非修行者、即时结果、重复请求确定性、跨适配器入口一致及资产完全不变。
- 道侣测试覆盖双方同意、拒绝/超时、已有关系冲突、解除双方确认/拒绝/超时、冷却、跨适配器身份、并发重复操作及无资产变化；另覆盖邀请规则冻结、内容关闭后的既有关系履约、历史 operation 重启回放、坏 JSON/快照拒绝与故障回滚重试。
- 师徒扩展只补新增行为测试；保留现有师徒测试和 QQ/OneBot 验收，不重写已经通过的生命周期。

## 开发顺序

1. 直接切磋的即时观战已开放；后续只补充独立规则切片，不改变双方资产边界。
2. 道侣关系建立、查询、解除和冷却已接入；后续再按独立切片补共享任务或双修。
3. 最后按独立切片补共享任务或双修；每个切片先更新内容 JSON 与本页规则，再实现领域逻辑和双适配器测试。
